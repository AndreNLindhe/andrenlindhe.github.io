Filmarkivet – datadriven applikation: CRUD, relationer och inloggning

Tjugosex steg som gör Filmarkivet till en applikation som går att förvalta utan att öppna en kodfil. Filmerna går att ändra och ta bort, varje film hör till en genre, sökningen görs av databasen, och allt som ändrar något ligger bakom en inloggning. Guiden är uppdelad efter lektionerna, så att du kan slå upp den del du behöver.

Missade du en lektion?

Guiden går att följa på egen hand. Så här hänger stegen ihop med passen, och ungefär hur lång tid de tar om du gör dem själv:

  • Lektion 36 (tis 19 jan) – steg 1 till steg 4, ungefär 90 minuter. Ändra och ta bort, och listvyn med sortering och sidor. Steg 3 har två fällor som ser ut att fungera fast de inte gör det – läs det stycket två gånger.
  • Lektion 37 (ons 20 jan) – steg 5 till steg 9, ungefär 75 minuter. Genren och relationen. I steg 6 kan migrationen avbrytas på din egen databas – det är väntat, och steget säger vad du gör.
  • Lektion 38 (tis 26 jan) – steg 10 till steg 13, ungefär 60 minuter. Slå på SQL-loggningen först – resten av stegen går inte att förstå utan den.
  • Lektion 39 (ons 27 jan) – steg 14 till steg 16, ungefär 45 minuter. Tre sorters validering. Skriv ditt eget attribut för en regel i din egen domän.
  • Lektion 40 (tis 2 feb) – steg 17 till steg 23, ungefär 90 minuter. Inloggningen. Hoppa inte över steg 21: där ser du att en dold länk inte skyddar något.
  • Lektion 41 (ons 3 feb) – steg 24, ungefär 20 minuter, och granskningen i uppgiftens etapp 4. Be någon granska din kod, även om du missade passet.
  • Lektion 43 (ons 10 feb) – steg 25 och steg 26, ungefär 30 minuter. Prova i ett testprojekt, inte i ditt eget.
  • Arbetspassen 42 och 44–47 – uppgiften, etapp för etapp. Varje etapp har en kontroll du gör själv.

Stegen bygger på varandra, men följer inte en rak linje genom ditt projekt: ändra- och ta bort-sidorna i steg 3 och 4 byggs utan genre, och får sin rullista i steg 9.

Två fel som inte syns

Det här området har fler fel än något tidigare som inte ger något felmeddelande alls: en ändring som inte sparas, en genre som inte visas, en sida som svarar fast länken är borta, en utloggning som går igenom utan token. Sidan ser rätt ut, terminalen är tyst.

Därför har varje steg en Kontrollera-rad. Gör den, också när allt ser ut att fungera. Tabellen När något går fel har de tysta felen med.

Koden går inte att kopiera

Kodblocken på den här sidan går inte att markera, och det är med flit. Att skriva av koden för hand är där en stor del av inlärningen sker: du läser raden, håller den i huvudet och upptäcker vid tangentbordet vad du inte förstod. Klistrar du in den hoppar du över precis det steget. Terminalkommandon och SQL är undantag – de är figurer, inte kod att öva på.

Steg 1 – Två operationer saknas

Vad vi gör. Ger tjänsten de två operationer den inte har.

Räkna vad IFilmService kan i dag. Den kan läsa – HamtaAllaAsync och HamtaAsync. Sedan område 5 kan den skapa – SkapaAsync. Den kan inte ändra och inte ta bort. Två av fyra bokstäver i CRUD saknas.

Filen. Services/IFilmService.cs, sist i gränssnittet:

    // Nya i område 6. Med dem är alla fyra CRUD-operationerna på plats:
    // HamtaAllaAsync/HamtaAsync läser, SkapaAsync skapar, UppdateraAsync
    // ändrar, TaBortAsync tar bort.
    Task UppdateraAsync(Film film);

    Task TaBortAsync(int id);

Filen. Services/FilmService.cs, två nya metoder:

    // Update säger åt contextet att hela objektet ska skrivas tillbaka. Filmen
    // kommer från formuläret och är inte spårad av det här contextet - därför
    // Update och inte bara SaveChangesAsync.
    public async Task UppdateraAsync(Film film)
    {
        using var db = await _fabrik.CreateDbContextAsync();
        db.Filmer.Update(film);
        await db.SaveChangesAsync();

        _logg.LogInformation("Film ändrad: {Titel} (id {Id})", film.Titel, film.Id);
    }

    public async Task TaBortAsync(int id)
    {
        using var db = await _fabrik.CreateDbContextAsync();
        Film? film = await db.Filmer.FindAsync(id);

        if (film is null)
        {
            _logg.LogWarning("Försökte ta bort film {Id} som inte finns", id);
            return;
        }

        db.Filmer.Remove(film);
        await db.SaveChangesAsync();

        _logg.LogInformation("Film borttagen: {Titel} (id {Id})", film.Titel, id);
    }

Varför det ser ut så. Båda metoderna följer mönstret från SkapaAsync: ett eget context från fabriken, en ändring, SaveChangesAsync. Det är skillnaden mellan dem som är intressant.

**Update tar emot en hel film.** Objektet kommer från formuläret i steg 3 och har aldrig varit i det här contextet. Contextet vet alltså ingenting om det, och SaveChangesAsync ensamt hade inte sparat någonting. Update säger: det här objektet finns redan i databasen, skriv tillbaka alla fält. EF Core letar upp raden med hjälp av Id. Det är därför id:t måste följa med formuläret, och det kommer att spela roll i steg 3.

**TaBortAsync tar emot bara ett id.** För att ta bort räcker det att veta vilken rad. Metoden hämtar filmen först, av två skäl: den kan redan vara borttagen, och loggraden vill ha titeln. Finns filmen inte loggas det och metoden gör ingenting. Att ta bort något som inte finns är inte ett fel värt att krascha för.

Gränssnittet växer av funktionalitet, inte av teknik. Samma sak som med SkapaAsync i område 5. Det står ingenting om databaser i IFilmService, och det ska det inte göra.

Kontrollera. dotnet build. Noll fel. Ingenting syns ännu – det finns ingen sida som anropar metoderna. Det är nästa steg.

I ditt projekt. Samma två metoder i ditt gränssnitt och din implementation, med dina namn. Parametertyperna följer samma mönster: hela objektet för att ändra, bara id för att ta bort.

@code {
    [SupplyParameterFromQuery(Name = "sortera")]
    public string? Sortera { get; set; }

    // En sträng och inte int?. Ett int? som får ?sida=abc kastar ett
    // undantag innan komponenten ens körs, och besökaren får en 500.
    [SupplyParameterFromQuery(Name = "sida")]
    public string? SidaFraga { get; set; }

    private const int PerSida = 4;

    private List<Film> sidan = new();
    private int antal;
    private int antalSidor = 1;

    // Sidan som visas. Den kommer ur adressen, och adressen kan vem som helst
    // skriva: ?sida=99 och ?sida=-3 ska ge en sida som finns, inte en tom tabell.
    private int sida = 1;

    // OnParametersSetAsync och inte OnInitializedAsync: värdena kommer ur
    // adressen, och adressen ändras när man klickar på en kolumnrubrik.
    protected override async Task OnParametersSetAsync()
    {
        List<Film> alla = await Arkivet.HamtaAllaAsync();

        IEnumerable<Film> ordnade = Sortera switch
        {
            "titel" => alla.OrderBy(f => f.Titel),
            "ar" => alla.OrderBy(f => f.Ar),
            "betyg" => alla.OrderByDescending(f => f.Betyg),
            _ => alla.OrderBy(f => f.Id)
        };

        antal = alla.Count;
        antalSidor = Math.Max(1, (int)Math.Ceiling(antal / (double)PerSida));
        // TryParse från område 2. Misslyckas den blir talet 0, och Clamp
        // gör 0 till 1.
        int.TryParse(SidaFraga, out int onskad);
        sida = Math.Clamp(onskad, 1, antalSidor);
        sidan = ordnade.Skip((sida - 1) * PerSida).Take(PerSida).ToList();
    }
}

Varför det ser ut så. Det är mycket på en gång, så ta det i tre delar.

En egen sida för administrationen. /filmer är besökarens lista, med kort och stjärnor. /admin/filmer är redaktörens: en tät tabell där varje rad går att ändra. Två sidor mot samma tjänst, med olika syften. I steg 22 får bara den ena kräva inloggning. Det hade inte gått om de varit samma sida.

Sorteringen ligger i adressen. Kolumnrubrikerna är vanliga länkar till ?sortera=titel, och [SupplyParameterFromQuery] läser värdet – samma sak som ?sok= i område 3. Den närliggande tanken är en knapp med @onclick, men under statisk serverrendering finns det ingen som tar emot klicket. Sidan har renderats färdigt och skickats. En länk fungerar alltid, för den gör en ny förfrågan. Varför knappen inte fungerar är en hel lektion, och den kommer i steg 25.

Att sorteringen står i adressen har en bieffekt som är värd något: den går att bokmärka och skicka till någon annan.

**switch-uttrycket väljer ordning.** Det är samma switch som i område 2, i den korta formen som ger ett värde. _ fångar allt annat, också null och ?sortera=hittepa. Ett okänt värde ger standardordningen, inte ett fel.

**Sidindelningen är två metoder: Skip och Take.** Sida 2 med fyra per sida betyder: hoppa över fyra, ta fyra. (sida - 1) * PerSida är hela uträkningen.

Sidnumret går inte att lita på. Adressen skriver besökaren själv, och ?sida=99, ?sida=-3 och ?sida=abc är lika lätta att skriva som ?sida=2. Därför läses numret som en sträng och tolkas med int.TryParse, och Math.Clamp håller det mellan 1 och sista sidan. Hade parametern varit int? hade ?sida=abc gett en 500 med Cannot parse the value 'abc' – innan en enda rad av din kod körts.

Allt som kommer ur adressen är något besökaren har skrivit. Behandla det så.

**OnParametersSetAsync, inte OnInitializedAsync.** Samma val som på detaljsidan i område 3. Klickar man på en kolumnrubrik är det samma sida med nya parametrar, och det är OnParametersSetAsync som körs då.

Sorteringen görs i C#, inte i databasen. Tjänsten hämtar alla filmer och sidan ordnar dem. Det är ett medvetet val, och det är lektion 38 som reder ut varför. Här räcker det att veta att det finns ett skäl.

Kontrollera. Gå till /admin/filmer. Sex filmer, fyra på första sidan. Klicka på Titel – adressen blir ?sortera=titel och ordningen ändras. Klicka på Nästa. Skriv sedan ?sida=99 i adressfältet för hand. Du ska hamna på sista sidan, inte på en tom tabell.

I ditt projekt. Din listvy med minst tre sorterbara kolumner. Välj en som är text, en som är ett tal och en till. PerSida får du bestämma, men välj ett tal som ger minst två sidor med din frödata – annars syns inte sidindelningen.

Filen. Validering/RimligtUtgivningsarAttribute.cs – ny mapp, ny fil:

using System.ComponentModel.DataAnnotations;

namespace Filmarkivet.Validering;

// Ett eget valideringsattribut, nytt i område 6.
//
// Varför inte [Range(1888, 2100)]? Därför att argumenten till ett attribut
// måste vara konstanter - de skrivs in i den kompilerade filen. Regeln här
// beror på vilket år det är när koden körs, och det vet kompilatorn inte.
//
// Attributet ärver ValidationAttribute och skriver över IsValid. Resten -
// när det körs, hur felet visas - sköter DataAnnotationsValidator, precis
// som för de inbyggda attributen.
public class RimligtUtgivningsarAttribute : ValidationAttribute
{
    public int Tidigast { get; set; } = 1888;

    // Hur många år fram i tiden som accepteras. Filmer annonseras i förväg,
    // så ett par år är rimligt.
    public int ArFramat { get; set; } = 2;

    protected override ValidationResult? IsValid(object? varde, ValidationContext sammanhang)
    {
        // Tomt fält är inte den här regelns ansvar. [Required] avgör om
        // fältet måste fyllas i; vi säger bara om det som står är rimligt.
        if (varde is null)
        {
            return ValidationResult.Success;
        }

        if (varde is not int ar)
        {
            return new ValidationResult("Året måste vara ett tal.",
                new[] { sammanhang.MemberName! });
        }

        int senast = DateTime.Now.Year + ArFramat;

        if (ar < Tidigast || ar > senast)
        {
            return new ValidationResult(
                $"Året måste ligga mellan {Tidigast} och {senast}.",
                new[] { sammanhang.MemberName! });
        }

        return ValidationResult.Success;
    }
}
